How the project uses IBM watsonx.ai watsonx.ai

DevPartner AI integrates IBM watsonx.ai (model: ibm/granite-3-8b-instruct) as the live AI brain of its verification pipeline. The integration is implemented in server/runner.mjs and called from the frontend via src/lib/ai.ts.

Architecture — how the call chain works

React UI (src/lib/ai.ts) → POST /functions/v1/ai-engine → server/runner.mjs → IBM IAM (token) → watsonx.ai REST API → Granite 3 8B

Authentication

The runner exchanges the WATSONX_API_KEY (IBM Cloud IAM API key) for a short-lived bearer token via https://iam.cloud.ibm.com/identity/token. Tokens are cached in memory and refreshed 60 seconds before expiry to avoid per-request latency.

// server/runner.mjs — IAM token exchange const body = new URLSearchParams({ grant_type: 'urn:ibm:params:oauth:grant-type:apikey', apikey: WATSONX_API_KEY, }); const res = await fetch(IAM_TOKEN_URL, { method: 'POST', headers: { 'Content-Type': 'application/x-www-form-urlencoded' }, body: body.toString(), });

Four specific pipeline actions powered by watsonx

1 — extract_intent

The developer's natural-language change request is sent to Granite with a structured prompt. Granite returns a JSON object containing the feature name, one-sentence summary, requirements, constraints, invariants, affected code areas, and a confidence score. This drives every downstream stage of the pipeline.

Prompt input Developer request string   Output Structured intent JSON

2 — generate_plan

Given the extracted intent, the affected files, and the risk level, Granite generates a structured multi-step implementation plan — including which files to touch, what tests to run at each step, and a rollback description. The developer reviews and approves this plan before any patch is applied.

Prompt input Intent + target files + risk score   Output Ordered step plan JSON

3 — hunt_counterexamples

The declared invariants are sent to Granite along with the change request. Granite is asked to actively search for adversarial boundary scenarios that could violate those invariants — forged roles, missing authorization headers, boundary conditions, etc. Any found violations are surfaced in the CounterexamplePanel.

Prompt input Invariant list + change request   Output Violations array + scenario count

4 — generate_evidence

After all verification stages pass, Granite generates a one-sentence auditable summary of the evidence — the final verdict, what was checked, and what held. This is combined with deterministic data (SHA-256 hash, timestamp) into the downloadable evidence report.

Prompt input Change request context   Output Verdict + evidence summary string

Graceful fallback design

Every watsonx call is wrapped in a try/catch. If the API key is absent, the endpoint is unreachable, or Granite returns unparseable output, the runner transparently falls back to deterministic local logic — so the pipeline always works, even without credentials. The ping action reports modelConfigured: true/false and environment: "watsonx-live" / "local-runner" so the UI can show the correct status badge.
